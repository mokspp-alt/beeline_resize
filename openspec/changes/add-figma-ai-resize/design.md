# Design

## Context

- Репозиторий пустой — это greenfield. Мотивация: см. proposal.md — Why.
- **Figma REST API не умеет создавать и менять узлы** — только читать. Записывать фреймы в файл может только плагин (Plugin API). Поэтому всё, что меняет документ, выполняется в плагине; бэкенд только думает.
- Плагин состоит из двух сред: `main` (sandbox с доступом к `figma.*`, без DOM и `fetch` к произвольным доменам) и `ui` (iframe с DOM и `fetch`). Сетевые запросы идут из `ui`, домены перечислены в `manifest.json` → `networkAccess.allowedDomains`.
- Библиотеки дизайн-системы доступны плагину через `figma.teamLibrary` (коллекции и переменные библиотеки), `figma.importComponentByKeyAsync`/`importComponentSetByKeyAsync`, `figma.variables.importVariableByKeyAsync`, `importStyleByKeyAsync`. Моды переменных на фрейме задаются `setExplicitVariableModeForCollection`.
- Перед изменением текстовых слоёв шрифты нужно загружать (`figma.loadFontAsync`).
- Тексты макетов на русском; LLM-провайдер выбирается в конфигурации (может быть в контуре РФ).

## Goals / Non-Goals

**Goals:**
- Монорепозиторий TypeScript: `packages/shared`, `packages/plugin`, `packages/backend`.
- Чёткая граница: LLM принимает **семантические** решения (роли, приоритеты, композиция), а точную геометрию считает детерминированный солвер. Это делает результат воспроизводимым и проверяемым.
- Результат — редактируемые фреймы с сохранёнными привязками к дизайн-системе.

**Non-Goals:**
- Экспорт в PNG/JPG/HTML и выгрузка в рекламные кабинеты (используется штатный экспорт Figma).
- Импорт токенов из кода (DTCG JSON, Style Dictionary) — только библиотека Figma в v1.
- Генерация нового контента (тексты, изображения) — только перекомпоновка существующего.
- Анимированные баннеры и прототипные связи.

## Decisions

### D1. Архитектура: плагин + stateless бэкенд
Плагин: захват исходника → запрос на бэкенд → применение планов. Бэкенд: роли + планы, без хранения макетов (кроме кэша на время запуска).
*Альтернативы:* (а) всё в плагине с ключом LLM в плагине — ключ утекает, нельзя менять провайдера централизованно; (б) REST API + рендер вне Figma — нельзя вернуть фреймы в Figma; (в) Figma MCP + агент — нет UI для дизайнеров и контроля над записью в документ.

### D2. Промежуточные форматы в `shared`
- **DesignIR** — нормализованное дерево исходника: `id`, `type`, `name`, `bbox` (относительно корня), `visible`, `constraints`, `autoLayout`, `text { characters, styleRef, fontSize, lineHeight }`, `fills` (с `variableRef`), `image { hash, scaleMode }`, `component { key, variantProps, overrides }`, `children`.
- **RoleMap** — `nodeId → { role, priority (0–100), group }`.
- **LayoutPlan** — на один целевой размер: `targetId`, `mode`, `composition` (шаблон из фиксированного словаря, например `row`, `stack`, `split-h`, `split-v`, `overlay`), список операций: `setLayout`, `reorder`, `hide`, `setSize`, `setTextSize`, `swapVariant`, `swapComponent`, `crop {focal}`, `bindVariable`.
Схемы описаны в zod; из них генерируются JSON Schema для structured output LLM и TS-типы для плагина и бэкенда.
*Почему операции, а не координаты от LLM:* модели плохо считают пиксели; операции проверяемы (`Plan validation`) и применимы к Figma напрямую.

### D3. Двухшаговый AI-пайплайн
1. **Анализ** (1 вызов на исходник): DesignIR + опц. превью → RoleMap. Кэшируется по хэшу DesignIR.
2. **Планирование** по **классу соотношения сторон** и режиму (например `banner:wide-strip`, `banner:square`, `web:mobile`, `app:ios-phone`), а не по каждому размеру: 300×250 и 336×280 получают один план-шаблон. Это сокращает число вызовов с ~30 до ~8 на полный запуск.
3. **Солвер** (детерминированный, без LLM) переводит план-шаблон в конкретную геометрию для каждого размера: auto layout Figma делает основную работу, солвер считает размеры шрифтов в пределах ограничений, кадрирование и safe area.
Вызовы шага 2 идут параллельно; плагин получает результаты потоково (SSE) и применяет по мере готовности.

### D4. Применение в Figma: clone → mode → variant → plan
Для каждого размера: `source.clone()` → `resize()` → установка явных модов переменных (брейкпоинт/платформа) → переключение вариантов и замена компонентов по конфигурации ДС → операции плана → привязка новых значений к ближайшим токенам. Сначала моды и варианты, потому что они уже решают большую часть адаптации «силами самой ДС»; план добивает остальное.
Инстансы компонентов считаются атомарными: внутрь инстанса солвер не лезет, только варианты/свойства. Опция «разрешить detach» выключена по умолчанию.
Весь запуск оборачивается в одну транзакцию undo (операции выполняются в одном синхронном блоке после получения всех данных, либо с `figma.commitUndo()` только в конце).

### D5. Конфигурация дизайн-системы Carnica
JSON-файл на бэкенде [`config/design-system.json`](../../../config/design-system.json), версионируется в репозитории. Дизайн-система разбита на шесть библиотек, у каждой своя роль:

| Роль | Библиотека | Что берём |
|---|---|---|
| `colors` | `01_Carnica-colors-2.0` | переменные/стили цвета, моды тем |
| `typography` | `02_Carnica-typography` | текстовые стили и переменные шрифта, моды брейкпоинтов (если есть) |
| `sizes` | `03_Carnica-sizes` | отступы, радиусы, размеры иконок и контролов, брейкпоинты/сетки |
| `icons` | `04_Carnica-icons` | компоненты иконок |
| `ui-kit-app` | `05_Carnica-UI-kit-APP` | компоненты для режима `app` |
| `ui-kit-web` | `06_Carnica-UI-kit-WEB` | компоненты для режима `web` (и `banner`, если в конфиге не указано иное) |

Структура конфигурации:
```json
{
  "designSystem": "Carnica",
  "libraries": {
    "colors":     { "name": "01_Carnica-colors-2.0",  "fileKey": "abOiwE5nz8PJ41TVWLQAYr" },
    "ui-kit-web": { "name": "06_Carnica-UI-kit-WEB", "fileKey": "et3X0ja6o9iITvuJZA1k5C" }
  },
  "kitByMode": { "web": "ui-kit-web", "app": "ui-kit-app", "banner": "ui-kit-web" },
  "collections": {
    "breakpoint": { "library": "sizes", "key": "<из скана>", "modes": { "mobile": "<из скана>", "tablet": "...", "desktop": "..." } },
    "platform":   { "library": "...",   "key": "<из скана>", "modes": { "ios": "...", "android": "..." } }
  },
  "variants": [{ "library": "ui-kit-web", "componentSet": "<из скана>", "property": "Size", "byClass": { "mobile": "M", "desktop": "L" } }],
  "substitutions": [{ "from": { "library": "ui-kit-web", "key": "..." }, "to": { "library": "ui-kit-app", "key": "..." }, "when": { "mode": "app" } }],
  "minFontSize": { "web": 12, "app": 12, "banner": 10 }
}
```
Плагин сопоставляет библиотеки по `name` (Plugin API отдаёт `libraryName` у коллекций переменных, file key ему недоступен), а `fileKey` используется бэкендом для REST API.

**Сканирование** (заполнение `<из скана>`):
- **Компоненты, наборы вариантов, стили** — бэкенд через REST API: `GET /v1/files/:key/component_sets`, `/components`, `/styles` по каждому `fileKey`. Нужен Figma personal access token (scope `file_content:read`, `library_content:read`) в переменной окружения `FIGMA_TOKEN`.
- **Переменные и моды** — из плагина через `figma.teamLibrary.getAvailableLibraryVariableCollectionsAsync()` и `getVariablesInLibraryCollectionAsync()`: REST-эндпоинт переменных доступен только на тарифе Enterprise.
- Результат — черновой JSON, который администратор проверяет. Соответствия WEB↔APP (`substitutions`) предлагаются автоматически по совпадению имён компонентов в двух китах и подтверждаются вручную.

*Альтернатива:* выводить все соответствия автоматически по именам — ненадёжно для произвольных названий модов и свойств; используется только как подсказка при сканировании.

### D6. Каталог размеров
Каталог по умолчанию из спеки `size-presets` лежит в `packages/shared/presets.ts`; командный каталог — `config/presets.json` на бэкенде, отдаётся плагину эндпоинтом `GET /config`. Safe area для экранов App хранится в каталоге рядом с размером. Пользовательские наборы — в `figma.clientStorage`.

### D7. Провайдеры LLM
Интерфейс `LlmProvider { generateStructured(schema, messages, opts) }` с адаптерами `anthropic`, `openai-compatible`, `gigachat`, `yandexgpt`. Для провайдеров без нативного structured output — JSON-режим + валидация zod + одна повторная попытка с текстом ошибки. Мультимодальность (превью) — по флагу возможностей адаптера; если не поддерживается, превью не отправляется.

### D8. Стек
- Плагин: TypeScript, сборка esbuild/Vite (`main` и `ui` отдельными бандлами), UI на Preact.
- Бэкенд: Node.js 22 + TypeScript, Fastify, zod, SSE для потоковой выдачи. Деплой — контейнер.
- Тесты: vitest; для `main` — мок `figma` API; golden-тесты солвера на фикстурах DesignIR.

### D9. API бэкенда
- `GET /config` → каталог размеров, конфигурация ДС, имя провайдера/модели, политика данных.
- `POST /adapt` (SSE) → вход: DesignIR, превью (опц.), список targetId, режимы; выход-поток: `roles`, затем `plan` для каждого targetId, `error`/`fallback` по размерам, `done`.
- Авторизация: `Authorization: Bearer <командный токен>`; SSO — следующий этап.

## Risks / Trade-offs

- [Недетерминированность LLM] → temperature 0, кэш RoleMap и планов по хэшу входа, строгая схема, валидация и детерминированный фолбэк.
- [Сложные исходники без auto layout (абсолютное позиционирование)] → предупреждение на этапе захвата; солвер работает с bbox; рекомендация дизайнерам собирать исходники на auto layout.
- [Инстансы нельзя перестраивать внутри] → атомарная обработка + варианты/замены из конфигурации ДС; detach только по явной опции.
- [Экстремальные пропорции (728×90 ↔ 1080×1920)] → отдельные классы композиций для баннеров и обязательное скрытие по приоритету вместо уменьшения текста ниже минимума.
- [Задержка и стоимость] → планирование по классам, параллельные вызовы, потоковое применение; лимиты на пользователя.
- [Утечка данных макета во внешнюю модель] → политика данных (запрет превью, маскирование текстов), провайдер в контуре РФ / on-prem через openai-compatible.
- [Каталог устройств устаревает] → командный каталог на бэкенде обновляется без релиза плагина.
- [Переменные Carnica не читаются через REST без Enterprise] → переменные и моды сканируются в плагине через `figma.teamLibrary`, REST — только для компонентов и стилей.
- [Нет доступа к файлам Carnica у токена бэкенда или у пользователя плагина] → проверка доступа при сканировании с понятной ошибкой по каждой библиотеке.
- [Изменения API Figma Variables/Library] → изоляция всех вызовов ДС в одном модуле плагина с тестами на моках.

## Migration Plan

Новый продукт, миграции нет. Раскатка: (1) приватный плагин в организации Figma для пилотной группы дизайнеров; (2) бэкенд в тестовом окружении с провайдером по умолчанию; (3) после пилота — публикация плагина в организации. Откат — снятие плагина с публикации; данные в файлах пользователей не затрагиваются.

## Open Questions

- Точные ключи коллекций, названия модов и список компонентов с вариантами в библиотеках Carnica заполняются в `config/design-system.json` после сканирования и на код не влияют.
- Есть ли в Carnica коллекции переменных с модами брейкпоинтов и платформ. Если нет, адаптация опирается только на варианты компонентов и замены WEB↔APP; набор задач от этого не меняется.
- Провайдер и модель по умолчанию для пилота — значение конфигурации.
- Нужен ли SSO на старте или достаточно командного токена — влияет только на настройку авторизации бэкенда.
